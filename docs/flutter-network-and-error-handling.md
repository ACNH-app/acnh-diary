# Flutter 데이터 접근 및 에러 처리 설계

- 작성일: 2026-03-12
- 대상 프로젝트: `nookipedia-api`
- 기본 데이터 경로: 로컬 DB 우선

## 1. 목표

1. 로컬 DB 실패와 외부 의존성 실패를 구분한다.
2. 사용자에게 과도한 전역 에러를 띄우지 않는다.
3. 로컬 저장 실패와 구매/광고 SDK 실패를 일관되게 처리한다.

## 2. 구성 요소

1. `ContentRepository`
2. `LocalStateRepository`
3. `PurchaseService`
4. `AdsService`
5. `AppErrorMapper`

## 3. 실패 유형

1. `LocalDatabaseError`
2. `MigrationError`
3. `PurchaseUnavailableError`
4. `PurchaseRestoreError`
5. `AdLoadError`
6. `UnknownError`

## 4. 재시도 정책

1. 로컬 DB 읽기 오류는 즉시 한 번만 재시도
2. 구매 복구 실패는 사용자 요청 시 재시도
3. 광고 로드 실패는 재시도하되 UX를 막지 않는다.
4. 로컬 저장 실패는 자동 무한 재시도하지 않는다.

## 5. 화면별 처리 규칙

1. 목록 첫 진입 실패
   - 콘텐츠 DB 열기 실패: 전체 에러 뷰
   - 상태 DB 실패: 읽기 전용 경고 배너
2. 상세 실패
   - 전체 에러 카드 + 재시도 버튼
3. 저장 실패
   - 화면 유지
   - 인라인 에러 또는 스낵바
4. 광고 SDK 실패
   - 즉시 모달 표시 금지
   - free 사용자에게만 빈 영역 또는 fallback 배너 허용
5. 구매 복구 실패
   - 설정 화면에서 재시도 CTA 제공

## 6. 데이터 접근 규칙

1. 콘텐츠 조회는 네트워크가 아니라 로컬 DB 조회를 기본으로 한다.
2. 광고 제거 여부는 entitlement 캐시와 스토어 복구 상태를 함께 본다.
3. 외부 네트워크는 광고 SDK와 스토어 SDK 호출 정도로 제한한다.

## 7. 로깅 및 관측성

1. dev 환경에서만 DB query error 상세 로깅
2. prod에서는 에러 종류와 화면 컨텍스트만 기록
3. 구매 상태와 광고 노출 여부는 분석 이벤트로 분리 가능

## 8. 테스트 포인트

1. 콘텐츠 DB 열기 실패
2. 상태 DB 쓰기 실패
3. 구매 복구 성공/실패
4. 광고 노출/광고 제거 전환
5. 네트워크가 완전히 없어도 핵심 기능 동작
