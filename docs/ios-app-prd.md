## 1. 제품 개요

### 1.1 한 줄 정의

Animal Crossing: New Horizons 플레이어가 주민, 카탈로그, 섬 정보와 일정을 iPhone에서 빠르게 조회하고 개인 진행 상태를 기록할 수 있는 관리 앱

### 1.2 해결하려는 문제

1. 현재 프로젝트는 웹 중심 구조라 iPhone에서 빠르게 확인하고 수정하는 경험이 약하다.
2. 주민/카탈로그/일정 확인은 짧은 세션에서 자주 일어나는데, 모바일 네이티브 탐색 구조가 없다.
3. 네트워크가 불안정한 상황에서도 최소한 최근 조회 데이터와 핵심 체크 기능을 유지할 수 있어야 한다.

### 1.3 목표

1. 주민/카탈로그 상태를 iPhone에서 2~3번의 탭 안에 확인하고 수정할 수 있게 한다.
2. 홈 화면에서 오늘 기준 요약 정보와 진행 상태를 빠르게 파악하게 한다.
3. 향후 로그인/멀티디바이스 동기화가 가능하도록 API 계약과 앱 구조를 분리해 둔다.

### 1.4 비목표

1. 1차 출시에서 Android 동시 지원은 포함하지 않는다.
2. 1차 출시에서 소셜 기능, 친구 공유, 커뮤니티 기능은 포함하지 않는다.
3. 1차 출시에서 서버 멀티유저 구조까지 완료하는 것을 필수 범위로 두지 않는다.

## 2. 대상 사용자

### 2.1 핵심 사용자

- Animal Crossing: New Horizons를 플레이하는 개인 사용자
- 카탈로그 수집, 주민 관리, 일정 메모를 자주 하는 사용자
- 한국어 UI와 빠른 상태 체크를 선호하는 사용자

### 2.2 주요 사용 시나리오

1. 외출 중 아이템을 보고 보유 여부를 바로 확인한다.
2. 새로운 주민을 만난 뒤 좋아하는 주민/우리 섬 주민 상태를 바로 바꾼다.
3. 오늘 방문 NPC, 현재 잡을 수 있는 생물, 개인 일정을 홈에서 확인한다.
4. 가구나 의류의 변형 보유 상태를 상세 화면에서 정리한다.

## 3. 출시 전략

### 3.1 1차 출시 권장 범위

포함:

1. 홈 요약
2. 주민 목록/검색/필터/상태 수정
3. 카탈로그 목록/상세/보유 체크
4. 변형 상태 체크
5. 섬 프로필 조회/수정
6. 플레이어 관리
7. 캘린더 일정 조회/추가/체크/삭제
8. 최근 조회 데이터 기반 읽기 캐시
9. 원격 이미지 디스크 캐시

제외:

1. 로그인
2. 멀티디바이스 동기화 보장
3. 소셜 로그인
4. 푸시 알림
5. Android 지원

### 3.2 출시 모델

1차 출시는 `개인용 단일 사용자 앱 + 기존 서버 재사용`을 기준으로 설계한다.

이유:

1. 현재 백엔드는 인증이 없고 상태 DB도 단일 사용자 구조다.
2. iOS 앱 전환의 첫 목표는 사용자 경험 개선이지 멀티유저 플랫폼 전환이 아니다.
3. 로그인/권한/유저 분리까지 같이 들어가면 범위가 크게 늘어난다.

단, 아래는 설계상 열어둔다.

1. 향후 `users` 테이블 추가
2. 인증 헤더 주입 가능한 네트워크 레이어
3. 상태 모델에 `updated_at` 또는 버전 필드 확장 가능성

## 4. 플랫폼/기술 방향

- 플랫폼: `iPhone`
- 최소 지원 버전: `iOS 17` 권장
- UI 프레임워크: `SwiftUI`
- 백엔드: 기존 `FastAPI`
- 데이터 소스: 기존 `/api/*`, `content.db`, 매핑 JSON
- 이미지: 서버가 제공하는 원격 URL + 일부 로컬 정적 자산 기반

선정 이유:

1. SwiftUI가 목록/탭/폼/시트 기반 앱 구조에 적합하다.
2. iOS 17 기준이면 Observation, NavigationStack, 최신 이미지/캐시 라이브러리 호환성이 좋다.
3. 기존 백엔드 API를 유지하면 모바일 전환 속도가 빠르다.

## 6. 기능 요구사항

### 6.1 홈

사용 API:

1. `GET /api/home/summary`
2. `GET /api/home/creatures-now`

요구사항:

1. 홈 상단에서 섬 프로필 요약과 전체 진행 상태를 보여준다.
2. 오늘 기준으로 현재 잡을 수 있는 생물을 보여준다.
3. 오늘 또는 이번 달 일정 요약을 보여준다.
4. 네트워크 실패 시 마지막 성공 데이터를 보여주고 재시도 버튼을 제공한다.

### 6.2 주민

사용 API:

1. `GET /api/villagers`
2. `GET /api/meta`
3. `POST /api/villagers/{villager_id}/state`
4. `POST /api/villagers/island-order`

요구사항:

1. 이름 검색, 성격 필터, 종 필터를 지원한다.
2. 좋아하는 주민, 우리 섬 주민, 과거 주민 상태를 수정할 수 있다.
3. 우리 섬 주민은 최대 10명 제한을 앱에서도 동일하게 안내한다.
4. 섬 주민 정렬은 편집 모드에서만 제공한다.

UX 결정:

1. 목록 셀에서 즉시 토글 가능한 액션은 최대 1~2개만 둔다.
2. 나머지 상태 변경은 상세 또는 액션 시트로 보낸다.

### 6.3 카탈로그

사용 API:

1. `GET /api/catalog/{catalog_type}/meta`
2. `GET /api/catalog/{catalog_type}`
3. `GET /api/catalog/{catalog_type}/{item_id}/detail`
4. `POST /api/catalog/{catalog_type}/{item_id}/state`
5. `POST /api/catalog/{catalog_type}/{item_id}/variations/{variation_id}/state`
6. 필요 시 `POST /api/catalog/{catalog_type}/state/bulk`

요구사항:

1. 카탈로그 타입별 목록을 빠르게 탐색할 수 있어야 한다.
2. 검색/필터/정렬을 지원하되 모바일에서는 bottom sheet로 단순화한다.
3. 상세 화면에서 보유, 기증, 수량, 변형 상태를 수정할 수 있어야 한다.
4. 첫 출시에서는 벌크 수정 UI를 기본 경로로 노출하지 않는다.

UX 결정:

1. 상세는 웹 모달 대신 풀스크린 push 화면으로 간다.
2. 목록 셀은 이름, 대표 이미지, 핵심 상태만 노출한다.
3. 변형이 많은 아이템은 섹션 리스트 또는 가로 스와이프 대신 단순 리스트를 우선한다.

### 6.4 섬 프로필/플레이어

사용 API:

1. `GET /api/profile`
2. `POST /api/profile`
3. `GET /api/players`
4. `POST /api/players`
5. `POST /api/players/{player_id}/main`
6. `DELETE /api/players/{player_id}`

요구사항:

1. 섬 프로필은 읽기 화면과 편집 화면을 분리한다.
2. 플레이어 목록에서 대표 플레이어를 명확히 구분한다.
3. 삭제는 확인 다이얼로그를 거친다.

### 6.5 캘린더

사용 API:

1. `GET /api/calendar`
2. `GET /api/calendar/annotations`
3. `GET /api/calendar/day`
4. `POST /api/calendar`
5. `POST /api/calendar/{entry_id}/checked`
6. `DELETE /api/calendar/{entry_id}`

요구사항:

1. 월간 캘린더와 날짜별 일정 목록을 제공한다.
2. 일정 추가/수정/체크/삭제를 지원한다.
3. 모바일에서는 일자 상세를 sheet 또는 push 화면으로 제공한다.
4. 날짜 선택은 iOS 기본 date picker를 사용한다.

## 7. 인증/계정 정책

1차 출시 결정:

1. 로그인 없음
2. 인증 헤더 없음
3. 단일 사용자 데이터 저장 전제

제약:

1. 서버 공개 배포 시 쓰기 API 보호가 되지 않는다.
2. 여러 디바이스의 동일 계정 동기화 개념이 없다.

대응:

1. 1차는 개인 서버 또는 제한된 배포를 전제로 한다.
2. 공개 배포 전에는 인증/멀티유저 설계를 별도 문서로 확정한다.

## 8. 오프라인 정책

1차 출시 결정:

1. 읽기 캐시 지원
2. 쓰기 오프라인 큐는 제한적 지원

세부 방침:

1. 최근 조회한 홈 요약, 주민 목록, 카탈로그 목록, 상세 데이터를 로컬 저장한다.
2. 보유 체크, 주민 상태 변경, 캘린더 수정은 네트워크 연결 시 즉시 전송을 기본으로 한다.
3. 오프라인 상태에서의 쓰기 요청은 1차 출시에서는 선택 기능으로 두고, 구현하더라도 보유 체크와 캘린더에 한정한다.
4. 오프라인 수정이 지원되지 않는 화면에서는 명확한 안내를 제공한다.

## 9. 이미지/캐시 정책

1. 주민/카탈로그 대표 이미지는 디스크 캐시를 사용한다.
2. 음악 이미지는 서버 정적 자산 URL을 사용하되 앱 캐시에 저장할 수 있게 한다.
3. 이미지 실패 시 앱 내 placeholder 이미지를 사용한다.
4. 캐시 상한은 초기값 `200MB` 수준으로 둔다.

## 10. 성능 목표

1. 홈 첫 콘텐츠 표시: 2초 이내
2. 주민 목록 첫 표시: 1.5초 이내
3. 카탈로그 첫 페이지 표시: 1.5초 이내
4. 상세 진입 체감 반응: 500ms 이내
5. 필터 반영 시간: 300ms 이내
6. 일반 스크롤에서 눈에 띄는 프레임 드랍이 없어야 한다.

## 11. 접근성 요구사항

1. 모든 주요 탭/버튼은 최소 `44pt` 터치 타깃을 가진다.
2. Dynamic Type 기본 지원을 목표로 한다.
3. VoiceOver 라벨을 주요 상태 토글과 탭에 제공한다.
4. 색상만으로 상태를 표현하지 않고 텍스트 또는 아이콘을 병행한다.

## 12. 성공 지표

1. 홈, 주민, 카탈로그의 핵심 플로우를 3탭 이내로 완료할 수 있다.
2. 사용자 테스트에서 보유 상태 수정 플로우를 별도 설명 없이 수행할 수 있다.
3. 앱 충돌 없이 주민/카탈로그/일정 주요 시나리오가 반복 수행된다.

## 13. 오픈 이슈

1. 공개 배포를 목표로 바꾸는 시점에 인증을 언제 도입할지
2. 오프라인 쓰기 큐를 1차에 넣을지 2차로 미룰지
3. 카탈로그 벌크 수정 기능을 iPhone에서도 노출할지
4. 이미지 저작권과 데이터 사용 조건을 App Store 제출 전 어떻게 정리할지

## 14. 출시 준비 완료 기준

1. API 계약 문서가 확정되어 앱/서버 필드가 고정된다.
2. 핵심 화면 와이어프레임과 UX 흐름이 승인된다.
3. 네트워크 실패/빈 상태/오류 상태 UI가 준비된다.
4. App Store 심사 리스크 문서 1차 검토가 끝난다.
