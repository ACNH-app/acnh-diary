# 모바일 로컬 저장/동기화 설계

- 작성일: 2026-03-12
- 대상 프로젝트: `nookipedia-api`

## 1. 목표

1. 앱 설치 후 핵심 데이터 조회가 로컬에서 가능해야 한다.
2. 사용자 상태는 모두 로컬 DB에 즉시 저장한다.
3. 네트워크 동기화 없이도 정합성을 유지한다.
4. 앱 업데이트 시 콘텐츠 데이터와 사용자 상태를 분리한다.

## 2. 저장 대상

1. 번들 콘텐츠 데이터
- 주민
- 카탈로그
- 이벤트/캘린더 기준 데이터
- 메타 데이터

2. 사용자 상태 데이터
- 주민 선호/섬 거주 여부
- 카탈로그 보유/변형 상태
- 일정
- 섬 프로필
- 플레이어 목록
- 광고 제거 entitlement 캐시

## 3. 저장소 구분

1. `content.db`
- 앱 번들 포함
- 읽기 전용

2. `app.db`
- 앱 실행 중 쓰기 가능
- 사용자 상태 저장

3. `secure storage`
- 구매 복구에 필요한 최소 플래그 저장
- 민감하지 않은 경우에도 일반 설정과 분리 가능

## 4. 초기 로드 정책

1. 앱 시작 시 번들 콘텐츠 DB를 연다.
2. 앱 상태 DB 스키마를 확인하고 마이그레이션을 적용한다.
3. 홈/목록/상세는 로컬 DB에서 즉시 조회한다.
4. 네트워크 fallback은 기본 경로가 아니다.

## 5. 저장 규칙

1. 사용자 액션은 DB에 즉시 반영한다.
2. 동일 항목의 상태 변경은 마지막 값만 유지하면 된다.
3. 서버 충돌 처리나 재시도 큐는 필요 없다.
4. 마이그레이션 실패 시 읽기 전용 안전 모드로 떨어질 수 있게 한다.

## 6. 앱 업데이트 정책

1. 콘텐츠 데이터 변경은 앱 업데이트와 함께 배포한다.
2. `content.db` 버전이 올라가도 `app.db` 사용자 상태는 보존한다.
3. 아이템 ID가 유지되는 범위에서는 보유 상태를 그대로 매핑한다.
4. 삭제되거나 이름이 바뀐 항목은 마이그레이션 규칙으로 흡수한다.

## 7. 사용자 노출 정책

1. 저장 성공은 조용한 인라인 피드백 위주로 처리한다.
2. 로컬 DB 오류는 전역 크래시 대신 복구 안내를 우선 표시한다.
3. 광고 제거 구매 상태는 앱 재시작 시 즉시 복원 확인을 시도한다.

## 8. 구현 메모

1. 로컬 저장소는 `sqflite` 또는 `isar` 중 하나로 통일한다.
2. 콘텐츠 조회용 schema와 사용자 상태 schema를 분리한다.
3. 오프라인/동기화 큐 provider는 제거하고 로컬 persistence provider로 치환한다.
