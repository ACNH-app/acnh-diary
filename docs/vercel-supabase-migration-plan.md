# Vercel + Supabase Migration Plan

기준 날짜: 2026-08-18

## 목표

- Vercel에는 현재 FastAPI + static SPA를 그대로 배포한다.
- 읽기 전용 콘텐츠 DB인 `content.db`는 우선 번들에 포함해 유지한다.
- 쓰기 상태 DB인 `app.db`는 Supabase Postgres로 옮긴다.
- 프런트 API 계약은 최대한 유지해서 UI 수정 범위를 줄인다.

## 지금 반영된 배포 뼈대

- Vercel 엔트리포인트: `app.index:app`
- Vercel 함수 번들 포함:
  - `static/**`
  - `data/**`
  - `content.db`
- 상태 저장용 `app.db`는 로컬 파일 기반이라 장기적으로 사용하지 않는다.

## 왜 이렇게 나누는가

현재 구조는 DB가 두 종류다.

- `content.db`
  - 주민, 카탈로그, 레시피 태그 같은 읽기 중심 데이터
  - 앱 배포 시점에 함께 실어도 된다
- `app.db`
  - 섬, 주민 상태, 카탈로그 보유, 플레이어, 캘린더 같은 사용자 상태
  - Vercel 로컬 파일시스템에 두면 데이터가 지속되지 않는다

따라서 1차 마이그레이션 범위는 `app.db`만 Supabase로 옮기는 것이 가장 효율적이다.

## 현재 상태 DB 마이그레이션 범위

Supabase로 옮길 대상 테이블:

- `island`
- `island_profile`
- `villager_state`
- `catalog_state`
- `catalog_variation_state`
- `calendar_entry`
- `player_profile`

유지 대상:

- `content.db`
- `data/*.json`

제외 대상:

- `app.db`
- `app.db-wal`
- `app.db-shm`

## 추천 타깃 구조

핵심 원칙:

- 사용자 구분은 `auth.users.id` 기반 UUID로 한다.
- `island`가 사용자 소유의 루트 엔티티가 된다.
- 대부분의 상태 테이블은 `island_id` 기준으로 묶는다.

### 권장 테이블 초안

```sql
create table public.island (
  id bigint generated by default as identity primary key,
  user_id uuid not null references auth.users(id) on delete cascade,
  name text not null default '',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.island_profile (
  island_id bigint primary key references public.island(id) on delete cascade,
  island_name text not null default '',
  nickname text not null default '',
  representative_fruit text not null default '',
  representative_flower text not null default '',
  birthday text not null default '',
  hemisphere text not null default 'north',
  time_travel_enabled boolean not null default false,
  game_datetime text not null default '',
  updated_at timestamptz not null default now()
);

create table public.villager_state (
  island_id bigint not null references public.island(id) on delete cascade,
  villager_id text not null,
  liked boolean not null default false,
  on_island boolean not null default false,
  camping_visited boolean not null default false,
  former_resident boolean not null default false,
  island_order integer not null default 0,
  updated_at timestamptz not null default now(),
  primary key (island_id, villager_id)
);

create table public.catalog_state (
  island_id bigint not null references public.island(id) on delete cascade,
  catalog_type text not null,
  item_id text not null,
  owned boolean not null default false,
  donated boolean not null default false,
  quantity integer not null default 0,
  updated_at timestamptz not null default now(),
  primary key (island_id, catalog_type, item_id)
);

create table public.catalog_variation_state (
  island_id bigint not null references public.island(id) on delete cascade,
  catalog_type text not null,
  item_id text not null,
  variation_id text not null,
  owned boolean not null default false,
  quantity integer not null default 0,
  updated_at timestamptz not null default now(),
  primary key (island_id, catalog_type, item_id, variation_id)
);

create table public.calendar_entry (
  id bigint generated by default as identity primary key,
  island_id bigint not null references public.island(id) on delete cascade,
  visit_date text not null,
  npc_name text not null,
  note text not null default '',
  checked boolean not null default false,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.player_profile (
  id bigint generated by default as identity primary key,
  island_id bigint not null references public.island(id) on delete cascade,
  name text not null default '',
  birthday text not null default '',
  is_main boolean not null default false,
  is_sub boolean not null default false,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

## 권장 RLS 방향

- 모든 상태 테이블은 `island.user_id = auth.uid()` 조건으로 접근 제한
- `island` 직접 조회 정책을 먼저 만들고, 나머지는 `exists (...)`로 연결
- 서비스 롤 키는 서버 전용으로만 사용
- 브라우저에는 `SUPABASE_SERVICE_ROLE_KEY`를 절대 노출하지 않는다

예시 방향:

- `select/insert/update/delete` on `island`
  - `user_id = auth.uid()`
- `select/insert/update/delete` on child tables
  - `exists (select 1 from public.island i where i.id = island_id and i.user_id = auth.uid())`

## 애플리케이션 코드 변경 순서

### 1. DB 접근 추상화

현재 SQLite 결합 지점:

- `app/core/db.py`
- `app/repositories/state.py`

우선 목표:

- 라우터/핸들러는 그대로 둔다
- 저장소 함수 시그니처를 최대한 유지한다
- 내부 구현만 SQLite에서 Postgres로 교체할 수 있게 나눈다

권장 구조:

- `app/core/state_store.py`
  - 저장소 인터페이스 또는 팩토리
- `app/repositories/state_sqlite.py`
  - 기존 구현 분리
- `app/repositories/state_postgres.py`
  - 신규 Supabase/Postgres 구현
- `app/repositories/state.py`
  - 환경변수 보고 적절한 구현 위임

### 2. 환경변수 기준 분기

권장 플래그:

- `DATABASE_URL`
  - 있으면 Postgres 사용
  - 없으면 기존 SQLite fallback

선택 플래그:

- `APP_STATE_BACKEND=sqlite|postgres`

### 3. SQL 실행 레이어 교체

현재는 `sqlite3` 전용 코드가 많다.

- `?` placeholder
- `sqlite3.Row`
- `PRAGMA`
- WAL / busy_timeout
- 마이그레이션을 Python 코드에서 직접 수행

Postgres 전환 시 해야 할 일:

- 드라이버 선택
  - `psycopg[binary]` 또는 `asyncpg`
- placeholder를 Postgres 방식으로 변경
- `PRAGMA` 제거
- 테이블 생성/수정은 Supabase SQL migration으로 이동

권장 1차 선택:

- 동기 코드 유지가 쉬운 `psycopg[binary]`

## 데이터 마이그레이션 순서

### Phase 1. 스키마 준비

- Supabase 프로젝트 생성
- 위 상태 테이블 생성
- RLS 정책 추가
- 로컬 개발용 테스트 계정 1개 생성

### Phase 2. SQLite export 스크립트 작성

새 스크립트 권장:

- `scripts/export_sqlite_state.py`
  - `app.db`에서 상태 테이블 읽기
  - JSON fixture 생성

출력 예시:

- `tmp/island.json`
- `tmp/island_profile.json`
- `tmp/villager_state.json`
- `tmp/catalog_state.json`
- `tmp/catalog_variation_state.json`
- `tmp/calendar_entry.json`
- `tmp/player_profile.json`

### Phase 3. Supabase import 스크립트 작성

새 스크립트 권장:

- `scripts/import_supabase_state.py`
  - `DATABASE_URL`로 연결
  - 사용자 계정과 섬 매핑
  - bulk insert 수행

### Phase 4. 애플리케이션 저장소 전환

- `state_postgres.py` 구현
- `DATABASE_URL` 설정 시 Postgres 사용
- 주요 API smoke test

### Phase 5. SQLite fallback 제거

Postgres가 안정화되면:

- Vercel에서는 SQLite fallback 비활성화
- `DB_PATH` 의존성 축소
