# iPhone 앱 전환 현재 상태 진단

- 작성일: 2026-03-12
- 대상 프로젝트: `nookipedia-api`
- 목적: 현재 레포를 기준으로 iPhone 앱 전환 시 재사용 가능한 부분, 새로 필요한 부분, 주요 위험요소를 정리한다.

## 1. 요약

현재 프로젝트는 `FastAPI` 백엔드와 `static` 기반 SPA가 한 저장소에 함께 있는 구조다. 데이터 본문은 `content.db`와 로컬 JSON 매핑을 사용하고, 사용자가 체크하는 상태는 `app.db` SQLite에 저장한다. 모바일 앱 전환 관점에서는 백엔드 조회 로직과 도메인 데이터는 상당 부분 재사용 가능하지만, 인증/사용자 분리/오프라인 동기화/이미지 캐시/App Store 배포 기준은 아직 별도 설계가 필요하다.

## 2. 현재 구조 기준 재사용 가능한 부분

### 2.1 백엔드 API와 도메인

재사용 가치가 높은 항목:

1. 카탈로그 조회 API
- `GET /api/catalog/{catalog_type}`
- `GET /api/catalog/{catalog_type}/meta`
- `GET /api/catalog/{catalog_type}/{item_id}/detail`

2. 주민 조회 API
- `GET /api/villagers`

3. 홈/메타 API
- `GET /api/home/summary`
- `GET /api/home/creatures-now`
- `GET /api/meta`

4. 사용자 상태 API 개념
- 섬 프로필
- 플레이어
- 캘린더
- 보유/기증/변형 상태

판단:
- API URL 구조와 도메인 개념은 모바일에서도 그대로 쓸 수 있다.
- 다만 응답 형식이 웹 전용 표시 필드와 섞여 있을 가능성이 있어, iOS용 계약 문서가 별도로 필요하다.

### 2.2 데이터 저장 구조

재사용 가치가 높은 항목:

1. `content.db` 중심의 읽기 구조
2. `data/*_name_map_ko.json` 기반 번역/매핑 체계
3. 음악 이미지 로컬 자산 관리 체계
4. `scripts/build_content_db.py` 기반 데이터 빌드 파이프라인

판단:
- 모바일 앱이 직접 이 자산을 읽는 구조가 아니라면, 서버 기준 데이터 소스로는 그대로 활용 가능하다.
- 장기적으로는 서버가 안정적인 JSON 응답만 제공하고, 앱은 DB/스크립트 내부 구조를 모르게 유지하는 편이 안전하다.

### 2.3 비즈니스 개념

재사용 가치가 높은 항목:

1. 주민 상태
- `liked`
- `on_island`
- `camping_visited`
- `former_resident`

2. 카탈로그 상태
- `owned`
- `donated`
- `quantity`

3. 보조 데이터
- 섬 프로필
- 플레이어 프로필
- 캘린더 일정

판단:
- 모바일 앱의 핵심 기능 정의는 이미 도메인 수준에서 상당 부분 존재한다.
- 따라서 모바일 전환의 핵심 비용은 "무엇을 만들지"보다 "어떻게 안전하게 사용할지"에 더 가깝다.

## 3. 새로 만들어야 할 부분

### 3.1 iOS 앱 클라이언트

현재 레포에는 iOS 앱 코드가 없다. 새로 정의해야 한다.

필수 항목:

1. 앱 구조
- SwiftUI 사용 여부
- 탭 구조
- 화면 계층 구조

2. 네트워크 계층
- 베이스 URL 주입
- 인증 헤더 주입
- 에러 매핑
- 재시도 정책

3. 앱 상태관리
- 서버 데이터 캐시
- 사용자 편집 중 상태
- 오프라인 대기 작업

4. 이미지 로딩
- 원격 이미지 캐시
- placeholder / fallback

### 3.2 모바일 전용 UX

현재 웹은 상단 네비게이션, 카드 그리드, 모달 중심이다. iPhone 앱에서는 별도 재설계가 필요하다.

필수 항목:

1. 하단 탭 또는 네이티브 내비게이션 구조
2. 모바일 목록 화면의 검색/필터/정렬 설계
3. 상세 화면의 push/sheet/fullscreen 정책
4. 터치 입력과 접근성 기준
5. 오프라인 상태 및 동기화 상태 표시

### 3.3 운영/배포

현재 레포는 웹 앱 실행을 전제로 한다. 모바일 앱 배포에는 아래가 추가로 필요하다.

1. 환경 분리 정책
2. TestFlight 배포 절차
3. 앱 버전 정책
4. 앱 설정값 관리
5. 크래시/성능 모니터링 도입

## 4. 인증/세션 구조 점검

### 4.1 현재 상태

코드 기준으로 확인되는 현재 상태:

1. 로그인 엔드포인트가 없다.
2. `/api/catalog/.../state`, `/api/villagers/.../state`, `/api/profile`, `/api/calendar`, `/api/players` 등 상태 변경 API에 인증 계층이 없다.
3. 상태 저장은 `app.db` SQLite 기반이며 단일 사용자 전제를 강하게 가진다.
4. 확장 로드맵 문서에서도 인증/멀티유저는 미래 단계로 정의되어 있다.

판단:
- 현재 구조는 로컬 또는 개인용 프로토타입으로는 충분하다.
- iPhone 앱을 공개 배포하거나 여러 기기에서 같은 계정을 쓸 계획이면 그대로는 부족하다.

### 4.2 iOS 앱 관점의 적합성

#### 단일 사용자, 개인용 앱으로 출시하는 경우

가능하다:

1. 로그인 없이 앱과 서버를 1:1로 운영
2. 사용자 상태를 서버 한 인스턴스의 단일 DB에 저장
3. 앱은 단순히 현재 웹 프런트 대신 네이티브 클라이언트 역할 수행

제약:

1. 디바이스별 사용자 구분이 없다.
2. 서버 URL이 공개되면 상태 변경 API가 보호되지 않는다.
3. 향후 계정 체계 도입 시 마이그레이션 비용이 커진다.

#### 공개 배포 또는 다중 사용자 앱으로 가는 경우

부족하다:

1. 사용자 식별이 없다.
2. 권한 검증이 없다.
3. 토큰 저장/만료/재발급 정책이 없다.
4. 데이터 격리 기준이 없다.

권장:

1. 최소한 `users` 테이블과 인증 계층을 먼저 설계
2. 기존 상태 테이블에 `user_id` 스코프 추가
3. 모바일은 Keychain 기반 토큰 저장을 전제로 설계

## 5. 모바일 전용 UX 필요 기능

현재 문서와 프런트 구조를 기준으로 iPhone 전용 설계가 필요한 기능은 아래와 같다.

1. 홈
- 요약 카드 우선순위 재정렬
- 작은 화면에서 캘린더와 오늘 잡을 수 있는 생물 표시 방식 단순화

2. 주민 목록
- 검색/필터를 네이티브 탐색 패턴으로 재설계
- 섬 주민 편집과 정렬 조작을 드래그 또는 편집 모드 기반으로 재설계

3. 카탈로그
- 많은 카테고리와 긴 필터 조합을 모바일에서 어떻게 압축할지 결정 필요
- 상세 모달은 웹보다 풀스크린 상세 화면이 더 적합

4. 캘린더
- 날짜 선택, 일정 추가, 체크 토글 흐름을 iOS 폼에 맞게 변경 필요

5. 설정/프로필
- 웹의 인라인 편집보다 별도 편집 화면이 더 적합

## 6. 오프라인 대응, 이미지 캐시, 성능 기준

### 6.1 오프라인 대응 현황

현재 구조는 서버 API 호출을 전제로 하며, 웹 프런트 자체의 오프라인 보장은 없다.

의미:

1. 앱에서 최근 조회 데이터 캐시 없이는 네트워크 단절 시 대부분 기능이 멈춘다.
2. 보유 체크나 캘린더 수정도 온라인 연결을 전제로 한다.

권장 방향:

1. 읽기 캐시
- 최근 조회한 주민/카탈로그/상세 응답 저장

2. 쓰기 큐
- 보유 체크
- 플레이어 수정
- 캘린더 수정

3. 동기화 정책
- 온라인 복귀 시 순차 재전송
- 실패 항목 재시도/취소 UX 정의

### 6.2 이미지 캐시 현황

현재 구조:

1. 일반 카탈로그/주민 이미지는 API 응답의 이미지 URL을 우선 사용
2. 음악 이미지는 로컬 정적 파일로 서빙
3. 실패 시 `/static/no-image.svg` 폴백 사용

모바일 전환 시 필요한 추가 결정:

1. 원격 이미지 캐시 라이브러리 또는 커스텀 캐시 사용
2. 캐시 용량 상한
3. 썸네일/원본 구분
4. 오프라인 fallback 자산 보유 범위

### 6.3 성능 기준

현재 레포에는 UI 성능 최적화 방향은 있으나, iPhone 앱용 수치 목표는 없다.

최소 권장 기준:

1. 홈 첫 렌더: 2초 이내
2. 카탈로그 첫 페이지 응답 후 첫 리스트 표시: 1.5초 이내
3. 상세 진입: 500ms 이내 체감 반응
4. 스크롤 중 눈에 띄는 프레임 드랍 없음
5. 필터 변경 후 결과 반영: 300ms 이내

## 7. App Store 심사 위험요소

### 7.1 데이터/저작권

확인 필요:

1. Nookipedia 기반 데이터와 이미지의 앱 배포 사용 조건
2. 로컬 저장 이미지 자산의 출처별 사용 범위
3. Animal Crossing 관련 명칭/이미지 사용 시 설명 문구 필요 여부

현재 상태:
- 레포에는 데이터 출처 문서는 있으나, App Store 제출 기준의 사용 권한 정리 문서는 없다.

### 7.2 계정/개인정보

확인 필요:

1. 로그인 도입 시 개인정보 처리방침 필요
2. 계정 생성 기능이 있으면 계정 삭제 경로 필요
3. 분석/크래시 SDK 도입 시 수집 항목 공개 필요

### 7.3 앱 완성도

확인 필요:

1. 모바일 앱이 단순 웹 포장처럼 보이지 않도록 네이티브 탐색/상태 처리가 필요
2. 미완성 메뉴, placeholder, 비어 있는 섹션은 제거 필요
3. 네트워크 실패 시 안내 없는 빈 화면이 나오면 심사 리스크가 커진다

## 8. 우선순위 권장안

구현 전에 아래 순서로 결정하는 편이 맞다.

1. 배포 모델 결정
- 개인용 앱
- 공개 배포 앱

2. 인증 전략 결정
- 무인증
- 계정 기반

3. 오프라인 범위 결정
- 읽기만 캐시
- 읽기/쓰기 동기화

4. 모바일 정보 구조 결정
- 탭
- 상세 진입 방식
- 검색/필터 UX

5. API 계약 고정
- 응답 형식
- 에러 형식
- 페이지네이션
