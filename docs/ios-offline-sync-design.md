# iOS 오프라인/동기화 설계

- 작성일: 2026-03-12
- 대상 프로젝트: `nookipedia-api`
- 목적: 현재 온라인 중심 API 구조를 iPhone 앱에서 어떻게 캐시하고, 어떤 범위까지 오프라인을 지원할지 정의한다.

## 1. 현재 상태

1. 웹 프런트는 서버 API 호출을 전제로 한다.
2. 서버 자체는 오프라인 동기화 개념이 없다.
3. 상태 변경 API는 즉시 서버 반영 방식이다.

## 2. 1차 출시 목표

1. 읽기 캐시 지원
2. 네트워크 실패 시 마지막 성공 데이터 노출
3. 쓰기 오프라인 지원은 제한적으로 설계

## 3. 캐시 대상

### 3.1 반드시 캐시

1. 홈 요약 마지막 응답
2. 주민 기본 목록
3. 카탈로그 타입별 첫 페이지
4. 마지막으로 본 상세 항목
5. 메타 데이터
- 주민 성격/종
- 카탈로그 메타

### 3.2 선택 캐시

1. 최근 검색 결과
2. 월간 일정 데이터
3. 현재 잡을 수 있는 생물 응답

## 4. 캐시 정책

1. 홈: 앱 실행 시 stale-while-revalidate
2. 주민 목록: 캐시 우선 후 백그라운드 새로고침
3. 카탈로그 목록: 첫 페이지 캐시 우선, 필터 결과는 네트워크 우선
4. 상세: 최근 본 데이터 우선 표시 후 새로고침

## 5. 쓰기 작업 분류

### 5.1 1차 즉시 전송 기본

1. 주민 상태 변경
2. 카탈로그 보유/기증/수량 변경
3. 변형 상태 변경
4. 캘린더 체크
5. 프로필 수정
6. 플레이어 저장/삭제

### 5.2 제한적 오프라인 후보

1. 카탈로그 보유 체크
2. 주민 상태 변경
3. 캘린더 추가/체크/삭제

제외 권장:

1. 플레이어 삭제
2. 대표 플레이어 변경
3. 섬 주민 순서 전체 재정렬

## 6. 오프라인 큐 설계

큐 아이템 필드:

1. `id`
2. `kind`
3. `path`
4. `method`
5. `payload`
6. `createdAt`
7. `retryCount`
8. `lastError`

처리 규칙:

1. FIFO 재전송
2. 같은 리소스에 대한 연속 상태 변경은 최신 항목으로 압축 가능
3. 4xx는 즉시 실패 처리
4. 네트워크 오류/5xx는 재시도

## 7. 동기화 충돌 정책

현재 서버는 버전 충돌 API가 없다. 1차 앱에서는 아래 정책을 쓴다.

1. 오프라인 수정이 켜져 있지 않으면 충돌 없음
2. 오프라인 수정이 켜져 있으면 last write wins 성격으로 처리
3. 차기 버전에서 `updated_at` 비교 또는 버전 필드 도입 검토

## 8. 사용자 UX

1. 캐시 데이터 표시 시 `마지막 업데이트` 시각 표시
2. 동기화 대기 중인 변경은 상태 배지 또는 토스트로 알림
3. 실패한 큐는 재시도 버튼 제공
4. 오프라인에서 불가능한 기능은 명확히 비활성화

## 9. 구현 우선순위

1. 읽기 캐시
2. 네트워크 실패 fallback
3. 카탈로그/주민 상태의 제한적 쓰기 큐
4. 캘린더 쓰기 큐

## 10. 차기 서버 개선 포인트

1. 상태 응답에 `updated_at` 노출
2. idempotency 키 또는 클라이언트 mutation id 지원
3. 충돌 시 `409` 응답 정의
