# iOS 인증/세션 설계

- 작성일: 2026-03-12
- 대상 프로젝트: `nookipedia-api`
- 목적: 현재 인증이 없는 서버 구조를 기준으로 iOS 앱의 인증 전략과 차기 확장 방향을 정의한다.

## 1. 현재 상태

1. 로그인 API가 없다.
2. 상태 변경 API에 인증이 없다.
3. 상태 테이블은 단일 사용자 기준이다.
4. 현재 PRD 기준 1차 출시는 로그인 없는 개인용 앱을 전제로 한다.

## 2. 1차 출시 정책

1. 인증 없음
2. 세션 저장 없음
3. 앱 내부에 로그인 화면 없음
4. 서버는 개인 또는 제한된 환경에서 운영하는 것을 전제

## 3. 현재 구조의 위험

1. 공개 서버 URL이 노출되면 쓰기 API가 보호되지 않는다.
2. 여러 사용자가 같은 서버를 쓰면 데이터가 섞인다.
3. 디바이스별 사용자 분리가 없다.

## 4. 1차 앱에서 필요한 최소 구조

로그인은 없지만 아래 인터페이스는 미리 둔다.

1. `AuthState`
2. `CredentialStore`
3. `AuthHeaderProvider`
4. `SessionInvalidationHandler`

현재 구현:

1. 모두 no-op 구현
2. 네트워크 레이어는 인증 헤더 없이 동작

이유:

1. 추후 로그인 도입 시 feature 코드 변경을 줄인다.

## 5. 차기 인증 권장안

공개 배포나 멀티디바이스 동기화를 목표로 할 때 권장:

1. 서버 인증 방식: `JWT + refresh token`
2. 앱 저장 위치:
- access token: 메모리 + 필요 시 Keychain
- refresh token: Keychain
3. 서버 변경:
- `users` 테이블 추가
- 상태 테이블에 `user_id` 추가
- 인증 미들웨어 추가

## 6. 세션 수명 정책 초안

차기 버전 기준 제안:

1. access token: 15분~1시간
2. refresh token: 30일
3. 앱 foreground 복귀 시 세션 유효성 점검
4. 401 발생 시 refresh 후 1회 재시도

## 7. 로그아웃/세션 만료 UX

차기 버전 기준:

1. 세션 만료 시 저장되지 않은 편집 상태를 보존
2. 재로그인 후 실패한 요청을 재시도 가능하게 함
3. 로그아웃 시 Keychain 자격증명 삭제

## 8. 보안 저장 규칙

1. 토큰은 Keychain 외 위치에 영속 저장하지 않는다.
2. 사용자 식별자와 환경 구분을 함께 저장한다.
3. 디버그 로그에 토큰을 남기지 않는다.

## 9. 서버 선행 작업

공개 배포 전 아래가 필요하다.

1. `users` 스키마 설계
2. `user_id` 기반 상태 데이터 분리
3. 비밀번호 해시 또는 OAuth 연동
4. 인증 없는 쓰기 API 차단
5. 계정 삭제 정책과 개인정보 처리방침 정리

## 10. 결론

현재 프로젝트 기준으로 1차 iOS 앱은 무인증으로 진행 가능하다. 다만 App Store 공개 배포나 다중 사용자 지원 전에는 이 문서를 기준으로 서버 인증 계층을 먼저 구현해야 한다.
