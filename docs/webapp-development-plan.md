# Web App Development Plan

기준 문서:
- `SRS.md`
- `SAD.md`
- `SDS.md`

기준 날짜: 2026-08-24

## 1. 목적

이 문서는 ACNH Diary 웹앱 MVP를 실제 구현 순서로 정리한 실행 계획서다.  
SRS의 기능 요구사항, SAD의 기술 선택, SDS의 모듈/데이터 설계를 기준으로 웹앱 범위를 확정하고, 현재 저장소 상태에 맞는 단계별 개발 우선순위를 정의한다.

## 2. 범위

MVP 웹앱 범위:
- 온보딩과 섬 생성/선택
- 오늘 화면
- 도감/카탈로그 화면
- 주민 화면
- 내 섬/사이드바 기반 섬 관리
- 루틴 체크
- NPC 방문 기록
- 날짜 전환과 섬별 데이터 분리
- FastAPI + Supabase 기반 상태 저장

MVP 제외 범위:
- 날씨 시드 입력 및 MeteoNook 연동
- 무주식 계산기
- 고급 공략 허브
- 일반 회원가입 플로우
- 모바일 앱 동기화
- 카탈로그 variation 단위 수집 관리 고도화

## 3. 현재 상태 요약

현재 저장소 기준 웹앱 상태:
- `frontend/`에 React + Vite 기반 라우팅 웹앱이 존재하며 MVP 화면 엔트리가 연결되어 있다.
- `Today`, `Catalog`, `Residents`, `MyIsland` 화면은 FastAPI 실데이터와 상태 API를 사용하고, 루틴/사진 상태처럼 백엔드 계약이 없는 항목은 섬별 `localStorage`로 격리한다.
- 프로필의 게임 날짜 변경은 전역 이벤트로 오늘 요약·루틴 날짜·사이드바 프로필을 함께 갱신한다.
- 주민 API는 성격/종족/서브타입 필터와 주민 상세 상태를 제공한다.
- `scripts/webapp_smoke_test.py`로 SQLite 로컬 API의 주요 읽기 경로를 자동 검증한다.
- 실제 런타임 배포 경로는 아직 `static/` + FastAPI 쪽이 중심이며, 신규 웹앱은 `frontend/`를 기준 구현체로 확장한다.

즉, 지금 필요한 일은 “새 웹앱 UI를 실제 API와 상태 모델에 연결하고, 배포 기준 화면으로 끌어올리는 것”이다.

## 4. 설계 기준

웹앱 구현 시 반드시 유지할 기준:
- 웹앱 MVP는 `React + TypeScript + Vite`를 기준으로 진행한다.
- 백엔드는 `FastAPI`를 유지하고, 상태 저장은 `Supabase PostgreSQL` 전환 방향에 맞춘다.
- 모든 사용자 데이터는 섬 기준으로 분리한다.
- 웹앱은 `오늘 / 도감 / 주민` 하단 내비게이션과 `내 섬` 사이드바 구조를 기본으로 한다.
- UI 컴포넌트와 화면 컴포넌트를 분리하고, 하드코딩 목업을 API 기반 화면으로 대체한다.
- Post-MVP 기능은 화면 슬롯만 남기거나 숨기되, 구현 범위에는 포함하지 않는다.

## 5. 개발 원칙

- 화면부터 완성하지 말고 데이터 계약과 상태 흐름을 먼저 고정한다.
- 현재 `static` 앱과 기능 중복이 생기더라도, 신규 웹앱은 `frontend/`를 기준 구현체로 삼는다.
- 새 웹앱은 최소한 다음 상태를 가져야 한다.
  - 로딩
  - 빈 상태
  - 에러 상태
  - 실제 데이터 상태
- 하드코딩 텍스트와 예시 수치는 API 응답 또는 명시적 mock 계층으로 분리한다.
- 화면은 모바일 우선으로 구현하되, 태블릿/데스크톱 확장 여지를 유지한다.

## 6. 단계별 개발 계획

## Phase 0. 기초 정리

목표:
- 웹앱 MVP의 구현 기준점을 고정한다.

작업:
- `frontend/`를 웹앱 주 구현 위치로 명시
- 라우팅/화면 엔트리 구조 설계
- 공통 타입, API 응답 타입, 화면 상태 타입 정의
- `GuideScreen` 등 Post-MVP 화면의 처리 방침 결정

완료 기준:
- 웹앱 정보 구조와 화면 목록이 고정된다.
- 각 화면이 어떤 API를 쓰는지 표로 정리된다.

## Phase 1. 앱 셸과 라우팅

목표:
- 단일 `TodayScreen` 중심 구조를 실제 웹앱 구조로 전환한다.

작업:
- React Router 도입
- 기본 경로 정의:
  - `/today`
  - `/catalog`
  - `/villagers`
  - `/my-island`
  - `/onboarding`
- `AppShell`, `BottomNavigation`, `Topbar`, `IslandSidebar`를 라우팅 구조에 맞게 재조립
- 활성 섬과 현재 날짜를 앱 전역 상태로 승격

완료 기준:
- 직접 URL 이동과 하단 탭 이동이 동작한다.
- 새로고침 후에도 현재 화면 진입이 안정적이다.

## Phase 2. 인증/초기 진입/섬 선택

목표:
- 사용자가 처음 진입했을 때 활성 섬 컨텍스트가 반드시 생기도록 만든다.

작업:
- 세션 체크 및 초기 로딩 게이트 추가
- 섬이 없으면 온보딩으로 이동
- 섬이 있으면 활성 섬 로드
- 섬 목록 조회, 섬 생성, 활성 섬 전환 연결
- 온보딩 입력 필드와 검증 반영

완료 기준:
- 첫 진입, 재진입, 다중 섬 전환 흐름이 모두 동작한다.

## Phase 3. 오늘 화면 실제화

목표:
- 현재 목업 중심 `TodayScreen`을 실데이터 화면으로 전환한다.

작업:
- 홈 요약 API 연결
- 날짜 전환 UI 연결
- 루틴 목록/완료 상태 연결
- 현재 가능한 생물 목록 연결
- 최근 NPC 방문 기록 연결
- 시즌/이벤트/생일 영역을 API 기반으로 렌더링

완료 기준:
- 오늘 화면이 하드코딩 없이 API 데이터로 구성된다.
- 섬 변경과 날짜 변경 시 요약 데이터가 함께 갱신된다.

## Phase 4. 도감/카탈로그 화면

목표:
- 검색, 카테고리, 수집 상태 변경이 가능한 도감 MVP를 완성한다.

작업:
- 카탈로그 목록 API 연결
- 검색/필터/정렬 상태 연결
- 카테고리 전환 연결
- 아이템 상세 보기 연결
- 보유/기증/채집 상태 업데이트 연결
- 섬별 수집 현황 분리 확인

완료 기준:
- 도감 화면에서 조회와 상태 변경이 모두 가능하다.
- 진행률 수치가 API 응답과 일치한다.

## Phase 5. 주민 화면

목표:
- 주민 검색과 상태 관리 기능을 웹앱에서 사용할 수 있게 한다.

작업:
- 주민 목록/검색 API 연결
- 성격/종족/서브타입 필터 연결
- 현재/위시/캠핑/과거 상태 관리 UI 구현
- 사진 보유 여부, 이사/캠핑 기록 편집 연결
- 주민 상세 패널 또는 상세 화면 연결

완료 기준:
- 주민 상태 기록이 섬별로 저장되고 다시 조회된다.

## Phase 6. 내 섬 화면과 관리 기능

목표:
- 섬 정보와 대표자 정보를 수정할 수 있게 한다.

작업:
- 섬 정보 요약/수정 UI 연결
- 대표자 프로필 수정 연결
- 섬 추가/수정/삭제 플로우 구현
- 삭제 전 영향 범위 경고와 확인 문구 처리

완료 기준:
- 활성 섬 기준 정보 수정이 가능하고, 다른 화면에도 즉시 반영된다.

## Phase 7. 품질 안정화

목표:
- 실제 사용 가능한 웹앱 수준으로 안정화한다.

작업:
- 에러/빈 상태/스켈레톤 정리
- 모바일/태블릿 반응형 보정
- 접근성 기본 점검
- 프론트엔드 smoke test 문서 갱신
- 핵심 흐름 테스트 작성

완료 기준:
- 온보딩, 오늘, 도감, 주민, 내 섬 핵심 플로우가 재현 가능하다.

## 7. 권장 구현 순서

추천 순서:
1. 앱 셸과 라우팅
2. 활성 섬/초기 진입 흐름
3. 오늘 화면 API 연결
4. 루틴/NPC 기록 연결
5. 도감 화면 연결
6. 주민 화면 연결
7. 내 섬 관리 기능
8. 에러 처리와 테스트

이 순서를 권장하는 이유:
- `오늘 화면`이 가장 많은 공통 상태를 사용한다.
- `활성 섬`과 `현재 날짜`를 먼저 고정해야 나머지 화면의 데이터 분리가 흔들리지 않는다.
- 도감과 주민은 공통 shell 위에 독립적으로 확장 가능하다.

## 8. API/상태 준비 항목

웹앱 구현 전에 계약이 필요한 항목:
- 활성 섬 조회 응답 형식
- 홈 요약 응답 형식
- 루틴 목록/업데이트 요청 형식
- 카탈로그 검색/필터 파라미터
- 아이템 수집 상태 upsert 형식
- 주민 상태 카테고리 저장 형식
- NPC 방문 기록 CRUD 형식

권장 위치:
- `frontend/src/api/*`
- `frontend/src/types/*` 또는 기능별 `types.ts`

## 9. 리스크

- 현재 `frontend/`는 프로토타입 텍스트와 예시 데이터가 많아 실제 상태 흐름과 쉽게 어긋날 수 있다.
- 기존 `static/` 앱과 신규 `frontend/`가 병행되면 구현 기준이 흔들릴 수 있다.
- 백엔드 API 이름과 응답 구조가 웹앱 설계와 어긋나면 화면 작업이 반복 수정될 가능성이 높다.
- 문서상 Post-MVP 기능이 UI에 남아 있으면 MVP 범위가 흐려질 수 있다.

## 10. 결정 필요 사항

개발 시작 전에 확정하면 좋은 항목:
- `frontend/`를 메인 웹앱 구현체로 확정할지 여부
- `GuideScreen`을 숨길지, 비활성 placeholder로 둘지 여부
- 앱 전역 상태를 `Context`로 갈지 별도 상태 라이브러리로 갈지 여부
- 라우팅을 hash가 아닌 history 기반으로 갈지 여부
- Supabase 인증 처리 범위를 프론트에서 어디까지 가질지 여부

## 11. 산출물

이 계획 기준 최종 산출물:
- 실제 동작하는 `frontend/` 웹앱
- 웹앱용 API 타입 정의
- 핵심 화면별 구현 완료 상태
- smoke test 문서
- 배포 가능한 웹앱 엔트리 구조
